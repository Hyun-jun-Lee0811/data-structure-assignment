# [자료구조2] Assignment 13 - 병합 정렬과 퀵 정렬의 성능 비교

## 과제

무작위 정수 데이터에 대해 **병합 정렬(Merge Sort)**과 **퀵 정렬(Quick Sort)**을 수행하고, 두 정렬 알고리즘의 성능 차이를 비교한다. 퀵 정렬은 세 가지 피벗 선택 방법(첫 번째 원소, 무작위 원소, 세 원소의 중앙값)을 적용하여 정렬 과정에서 발생하는 **숫자 비교 횟수, 실행시간, 최대 추가 메모리 사용량**을 측정하고 분석한다.

- 데이터 크기: n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 데이터 구성: `rand()`로 생성한 무작위 정수
- 정렬 기준: 오름차순
- 구현 알고리즘: Merge Sort, Quick Sort (First Pivot), Quick Sort (Random Pivot), Quick Sort (Median-of-Three)
- 측정 항목: 숫자 비교 횟수, 실행시간(ms), 최대 추가 메모리 사용량(Byte)
- 추가 분석: 데이터 크기 증가에 따른 비교 횟수 및 실행시간 변화, 피벗 선택 방법에 따른 성능 차이, 시간 복잡도와 공간 복잡도 비교

## 구현 내용

### 1. 데이터 생성

- 데이터 크기 `n`마다 원본 배열(`original`)을 `rand()`를 사용하여 한 번만 생성
- 각 정렬 알고리즘마다 원본 배열을 작업용 배열(`work`)에 복사하여 사용하므로, 모든 알고리즘이 **동일한 데이터**를 정렬
- 데이터 생성과 배열 복사는 비교 횟수 및 실행시간 측정에서 제외
- `srand((unsigned int)time(NULL))`를 사용하여 실행할 때마다 다른 무작위 데이터 생성

### 2. 정렬 알고리즘

| 알고리즘 | 구현 방식 |
|---|---|
| Merge Sort | 배열을 절반씩 나누어 정렬한 후 병합 |
| Quick Sort (First) | 현재 정렬 구간의 첫 번째 원소를 피벗으로 선택 |
| Quick Sort (Random) | 현재 정렬 구간에서 무작위 위치의 원소를 피벗으로 선택 |
| Quick Sort (Median3) | 첫 번째, 가운데, 마지막 원소 중 중앙값을 피벗으로 선택 |

- **Merge Sort:** 배열을 재귀적으로 절반씩 분할하고, 정렬된 두 구간을 임시 배열에 병합한 뒤 원래 배열에 복사
- **Quick Sort (First):** `low` 위치의 원소를 피벗으로 사용
- **Quick Sort (Random):** `low + rand() % (high - low + 1)`을 통해 현재 정렬 구간에서 무작위 위치를 선택
- **Quick Sort (Median3):** 첫 번째, 가운데, 마지막 원소의 값을 비교하여 크기순으로 중앙에 위치하는 값을 피벗으로 선택
- 퀵 정렬은 피벗을 선택하는 부분만 다르게 구현하고, 나머지 분할 알고리즘(`partition`)은 동일하게 유지
- 퀵 정렬은 피벗을 선택한 후 해당 원소를 구간의 마지막 위치로 이동시키고, 피벗 이하의 값은 왼쪽, 피벗보다 큰 값은 오른쪽으로 분할
- 분할이 끝나면 피벗을 최종 위치에 배치하고, 왼쪽과 오른쪽 구간에 대해 재귀적으로 정렬 수행
- 라이브러리 정렬 함수(`qsort` 등)는 사용하지 않음

### 3. 비교 횟수 측정

- **Merge Sort:** 병합 과정에서 두 부분 배열의 원소를 비교할 때마다 비교 횟수를 1 증가
- **Quick Sort:** 분할 과정에서 `arr[j] <= pivot`을 수행할 때마다 비교 횟수를 1 증가
- **Median-of-Three:** 중앙값을 결정하기 위해 발생하는 데이터 값 사이의 비교도 포함
- 비교 결과가 참인지 거짓인지와 관계없이 데이터 값 비교 1회를 계산
- 반복문의 인덱스 및 종료 조건 검사 등 데이터 값 비교가 아닌 연산은 포함하지 않음
- 피벗의 무작위 위치 생성과 데이터 이동 및 교환은 비교 횟수에 포함하지 않음
- 정렬 결과 검증(`isSorted`)은 비교 횟수에 포함하지 않음
- 각 알고리즘의 비교 횟수를 초기화한 뒤 정렬을 수행하고, 정렬이 끝나면 `isSorted()`로 오름차순 여부를 확인

### 4. 실행시간 측정

- `clock()`을 사용하여 각 정렬 알고리즘의 실행시간 측정
- 데이터 크기별 반복 측정을 통해 평균 실행시간 계산
- 실행시간 측정 전 작업용 배열에 원본 데이터를 복사
- 데이터 생성, 배열 복사, 결과 출력 및 정렬 검증 시간은 측정에서 제외
- Merge Sort와 Quick Sort의 실행시간을 동일한 데이터 크기에서 비교
- Quick Sort는 First, Random, Median-of-Three 세 가지 피벗 선택 방법을 각각 측정

### 5. 메모리 사용량 측정

- 정렬 과정에서 발생하는 추가 메모리 사용량을 Byte 단위로 측정
- **Merge Sort:** 병합 과정에서 사용하는 임시 배열의 크기와 재귀 호출에 따른 스택 사용량을 고려
- **Quick Sort:** 별도의 병합용 임시 배열 없이 원본 배열 내부에서 정렬하며, 재귀 호출에 따른 스택 사용량을 고려
- 재귀 호출 과정에서 지역 변수의 주소와 호출 깊이를 추적하여 스택 메모리 사용량을 추정
- Merge Sort의 임시 배열은 `n * sizeof(int)`를 기준으로 계산
- 측정 결과는 정렬 과정에서 발생하는 추가 메모리 사용량의 추정치이며, 운영체제에서 측정한 전체 프로세스 메모리 사용량과는 다름

## 결과 분석

### 1. 데이터 크기 증가에 따른 비교 횟수 변화

- **Merge Sort:** 데이터 크기가 2배가 될 때 비교 횟수는 약 2.17~2.23배 증가하였다. 병합 정렬은 배열을 절반씩 분할하고 각 단계에서 병합을 수행하므로 데이터 크기가 증가해도 비교 횟수가 비교적 일정한 비율로 증가하였다.
- **Quick Sort (First):** 비교 횟수는 약 2.05~2.28배 증가하였으며, 16,000개에서 20,000개로 증가할 때는 1.35배 증가하였다. 첫 번째 원소를 피벗으로 사용하기 때문에 피벗이 선택되는 위치와 데이터 분포에 따라 분할 결과가 달라질 수 있다.
- **Quick Sort (Random):** 비교 횟수는 약 1.95~2.33배 증가하였다. 무작위 피벗을 선택하기 때문에 분할 결과가 실행마다 달라질 수 있으며, 이번 실험에서도 데이터 크기에 따른 비교 횟수 증가율이 일정하지 않았다.
- **Quick Sort (Median3):** 비교 횟수는 약 2.09~2.25배 증가하였다. 세 원소 중 중앙값을 피벗으로 선택하여 극단적인 피벗이 선택될 가능성을 줄였으며, 전반적으로 일정한 증가 추세를 보였다.
- 전체적으로 네 알고리즘 모두 데이터 크기가 증가함에 따라 비교 횟수가 증가하였다. 특히 Merge Sort는 모든 데이터 크기에서 가장 적은 비교 횟수를 기록하였다.

### 2. 병합 정렬과 퀵 정렬의 실행시간 차이

- **Merge Sort:** 모든 데이터 크기에서 실행시간이 증가하였다. 병합 과정에서 두 부분 배열의 원소를 비교하고 임시 배열에 저장한 다음 원래 배열로 다시 복사하는 작업이 발생한다.
- **Quick Sort:** 배열 내부에서 원소를 교환하면서 정렬하므로 별도의 병합용 임시 배열을 사용하지 않는다. 이러한 특성으로 인해 이번 실험에서는 대부분 Merge Sort보다 빠른 실행시간을 기록하였다.
- 1,000개와 2,000개 데이터에서는 Quick (First)가 가장 빠르게 측정되었다. 4,000개 이상의 데이터에서는 Quick (Median3)가 가장 빠른 실행시간을 기록하였다.
- 20,000개 데이터 기준으로 Merge Sort는 3.0900ms, Quick (First)는 2.6800ms, Quick (Random)은 3.0100ms, Quick (Median3)는 2.4300ms로 측정되었다.
- 특히 Quick (Median3)는 Merge Sort보다 약 21.4% 짧은 실행시간을 기록하였다.
- 다만 Quick Sort의 실행시간은 피벗 선택과 분할 결과에 영향을 받으며, Random Pivot의 경우 무작위 선택에 따른 추가 연산도 발생한다. 따라서 실행시간이 항상 동일한 순서로 나타나는 것은 아니다.

### 3. 병합 정렬과 퀵 정렬의 메모리 사용량 차이

- **Merge Sort:** 병합 과정에서 크기가 n인 임시 배열을 추가로 사용한다. 따라서 데이터 크기가 증가할수록 임시 배열의 메모리 사용량도 증가한다. 여기에 재귀 호출 과정에서 사용하는 스택 메모리가 추가된다.
- **Quick Sort:** 별도의 병합용 임시 배열 없이 원본 배열 내부에서 원소를 교환하며 정렬한다. 따라서 주로 재귀 호출에 따른 스택 메모리가 추가로 사용된다.
- 20,000개 데이터 기준으로 Merge Sort는 84,928 Bytes를 사용한 반면, Quick (First)는 10,848 Bytes, Quick (Random)은 10,272 Bytes, Quick (Median3)는 7,392 Bytes로 측정되었다.
- Merge Sort는 임시 배열을 사용하기 때문에 퀵 정렬보다 추가 메모리 사용량이 크게 나타났다.
- 퀵 정렬 세 가지 방식 중에서는 Median-of-Three가 모든 데이터 크기에서 가장 낮은 메모리 사용량을 기록하였다. 이는 이번 실험에서 해당 방식의 재귀 호출 과정에서 측정된 스택 사용량이 상대적으로 작았기 때문이다.
- 다만 퀵 정렬의 스택 사용량은 피벗에 따른 분할 균형과 재귀 호출 깊이에 따라 달라질 수 있다.

### 4. 퀵 정렬의 피벗 선택 방법에 따른 성능 차이

- **First Element:** 현재 정렬 구간의 첫 번째 원소를 피벗으로 선택한다. 구현이 간단하지만 피벗이 최솟값이나 최댓값에 가까운 경우 분할이 한쪽으로 치우칠 수 있다. 이번 실험에서는 20,000개 데이터에서 353,422회로 퀵 정렬 세 방식 중 가장 많은 비교 횟수를 기록하였다.
- **Random Pivot:** 현재 정렬 구간에서 무작위 위치의 원소를 피벗으로 선택한다. 특정 위치에 대한 의존성을 줄일 수 있지만 무작위 선택이 항상 균형 잡힌 분할을 보장하지는 않는다. 실제로 8,000개 데이터에서는 126,452회로 퀵 정렬 세 방식 중 가장 많은 비교 횟수를 기록하였다.
- **Median-of-Three:** 첫 번째, 가운데, 마지막 원소 중 중앙값을 피벗으로 선택한다. 세 위치의 값을 비교하여 극단적인 피벗이 선택될 가능성을 줄이고 상대적으로 균형 잡힌 분할을 유도한다. 이번 실험에서는 4,000개, 8,000개, 20,000개 데이터에서 퀵 정렬 방식 중 가장 적은 비교 횟수를 기록하였다.
- 20,000개 데이터 기준으로 Median-of-Three는 312,293회로 First Element의 353,422회보다 약 11.6% 적은 비교를 수행하였다.
- 실행시간에서도 Median-of-Three는 4,000개 이상의 데이터에서 가장 빠른 결과를 기록하였다.
- 다만 작은 데이터에서는 피벗을 선택하기 위한 추가 비교가 전체 성능에 영향을 줄 수 있으며, 실제 실험에서도 1,000개와 2,000개 데이터에서는 First Element가 더 빠르게 측정되었다.
- 따라서 피벗 선택 방법에 따른 성능은 데이터 크기와 실제 분할 결과에 따라 달라지며, 이번 실험에서는 큰 데이터에서 Median-of-Three가 전반적으로 좋은 결과를 보였다.

### 5. 시간 복잡도 및 공간 복잡도 비교

| 알고리즘 | 평균 시간 복잡도 | 최악 시간 복잡도 | 공간 복잡도 |
|---|---|---|---|
| Merge Sort | O(n log n) | O(n log n) | O(n) |
| Quick Sort (First) | O(n log n) | O(n²) | 평균 O(log n), 최악 O(n) |
| Quick Sort (Random) | O(n log n) | O(n²) | 평균 O(log n), 최악 O(n) |
| Quick Sort (Median3) | O(n log n) | O(n²) | 평균 O(log n), 최악 O(n) |

- **Merge Sort:** 배열을 절반씩 나누어 정렬한 후 병합하는 과정을 반복한다. 분할 단계는 log n이고 각 단계에서 전체 n개의 원소를 처리하므로 시간 복잡도는 최선, 평균, 최악의 경우 모두 O(n log n)이다. 다만 병합을 위한 임시 배열이 필요하므로 추가 공간 복잡도는 O(n)이다.
- **Quick Sort:** 피벗을 기준으로 배열을 분할하고 양쪽 구간을 정렬한다. 분할이 균형 있게 이루어지면 평균적으로 O(n log n)의 시간 복잡도를 갖지만, 한쪽으로 치우친 분할이 반복되면 O(n²)의 최악 시간 복잡도가 발생한다.
- 퀵 정렬은 별도의 병합용 배열을 사용하지 않으며, 평균적으로 재귀 호출 스택에 O(log n)의 공간을 사용한다. 하지만 최악의 경우 재귀 깊이가 n에 가까워져 O(n)의 공간이 필요할 수 있다.
- 피벗 선택 방법은 평균적인 분할의 균형에 영향을 줄 수 있지만, First, Random, Median-of-Three 모두 이론적인 최악 시간 복잡도는 O(n²)이다.

### 6. 메모리 사용량 측정 방법과 계산 기준

이번 실험에서는 정렬 과정에서 발생하는 추가 메모리 사용량을 추정하기 위해 재귀 호출에 따른 스택 사용량과 정렬 과정에서 할당하는 임시 배열의 크기를 고려하였다.

- **Merge Sort:** 병합 과정에서 사용하는 임시 배열의 크기를 `n * sizeof(int)`로 계산하고, 재귀 호출 과정에서 추정한 스택 사용량을 더하였다.
- **Quick Sort:** 별도의 병합용 임시 배열을 사용하지 않으므로 재귀 호출 과정에서 추정한 스택 사용량을 기준으로 계산하였다.
- 재귀 호출 과정에서 지역 변수의 주소를 추적하고 호출 프레임의 주소 차이를 이용하여 스택 메모리 사용량을 추정하였다.
- 메모리 사용량은 Byte 단위로 출력하였다.

20,000개 데이터에서 Merge Sort의 메모리 사용량은 84,928 Bytes이다. 이 중 임시 배열은 `20,000 * sizeof(int)`로 계산되며, 일반적인 4 Byte 정수 환경에서는 80,000 Bytes이다. 나머지는 재귀 호출 스택에 대한 추정치이다.

반면 Quick Sort는 별도의 임시 배열이 없으므로 재귀 호출에 따른 스택 사용량이 주된 추가 메모리 사용량이다. 따라서 이번 실험에서 Merge Sort가 퀵 정렬보다 큰 메모리 사용량을 기록한 것은 병합 과정에서 사용하는 임시 배열의 영향이 크다고 볼 수 있다.

단, 주소를 이용한 스택 메모리 추정은 실제 프로세스의 최대 메모리 사용량을 직접 측정한 값이 아니다. 컴파일러의 최적화 설정과 함수의 스택 프레임 구성 등에 따라 달라질 수 있으므로, 본 실험에서는 알고리즘별 추가 메모리 사용량을 비교하기 위한 추정값으로 활용하였다.

## 결론

이번 과제에서는 무작위 정수 데이터 n = 1,000 ~ 20,000에 대해 병합 정렬과 세 가지 피벗 선택 방법을 사용하는 퀵 정렬의 비교 횟수, 실행시간, 메모리 사용량을 측정하고 성능을 분석하였다.

- **비교 횟수:** Merge Sort는 모든 데이터 크기에서 가장 적은 비교 횟수를 기록하였다. 배열을 일정하게 절반씩 분할하고 병합하는 방식이 비교 횟수의 안정적인 증가에 영향을 준 것으로 판단된다.
- **실행시간:** 퀵 정렬은 대부분의 데이터 크기에서 Merge Sort보다 빠른 실행시간을 기록하였다. 특히 20,000개 데이터에서 Quick (Median3)는 2.4300ms로 가장 빠른 결과를 보였다.
- **메모리 사용량:** Merge Sort는 병합을 위한 임시 배열을 사용하기 때문에 퀵 정렬보다 많은 추가 메모리를 사용하였다. 20,000개 데이터 기준 Merge Sort는 84,928 Bytes, Quick (Median3)는 7,392 Bytes로 측정되었다.
- **피벗 선택 방법:** First Element는 피벗이 한쪽으로 치우칠 가능성이 있고, Random Pivot은 무작위 선택으로 인해 분할 결과가 실행마다 달라질 수 있다. Median-of-Three는 세 원소의 중앙값을 선택하여 상대적으로 균형 잡힌 분할을 유도하였다.
- **시간 및 공간 복잡도:** Merge Sort는 최악의 경우에도 O(n log n)의 시간 복잡도를 유지하지만 O(n)의 추가 공간이 필요하다. 퀵 정렬은 평균 O(n log n)의 시간 복잡도와 평균 O(log n)의 추가 스택 공간을 갖지만, 최악의 경우 시간 복잡도는 O(n²)까지 증가할 수 있다.
- **메모리 측정:** 임시 배열과 재귀 호출 스택을 기준으로 추가 메모리 사용량을 추정하였다. 실제 프로세스 전체 메모리 사용량과는 차이가 있을 수 있지만, 두 알고리즘의 메모리 구조 차이를 비교하는 데 활용하였다.

종합적으로 이번 실험에서는 Merge Sort가 비교 횟수 측면에서 가장 적은 연산을 수행하였으며, Quick Sort는 추가 메모리 사용량과 실행시간 측면에서 유리한 결과를 보였다. 특히 Quick (Median3)는 큰 데이터에서 비교 횟수와 실행시간 모두 퀵 정렬의 다른 피벗 방식보다 좋은 결과를 나타냈다.

이를 통해 정렬 알고리즘의 성능은 단순히 비교 횟수만으로 결정되는 것이 아니라, 데이터 이동, 임시 메모리 사용, 피벗 선택에 따른 분할 균형 등 여러 요소의 영향을 받는다는 것을 확인하였다.
