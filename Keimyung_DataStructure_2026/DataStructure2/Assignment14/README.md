# [자료구조2] Assignment 14 - 힙 정렬, 병합 정렬 및 퀵 정렬의 성능 비교

## 과제

무작위 정수 데이터에 대해 힙 정렬(Heap Sort), 병합 정렬(Merge Sort), 퀵 정렬(Quick Sort)을 수행하고, 세 정렬 알고리즘의 성능을 비교한다.

퀵 정렬은 세 가지 피벗 선택 방법(첫 번째 원소, 무작위 원소, 세 원소의 중앙값)을 적용하여 정렬 과정에서 발생하는 **숫자 비교 횟수, 실행시간, 최대 추가 메모리 사용량**을 측정하고 분석한다.

- 데이터 크기: n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 데이터 구성: `rand()`로 생성한 무작위 정수
- 데이터 범위: 0 ~ 99,999
- 정렬 기준: 오름차순
- 구현 알고리즘: Heap Sort, Merge Sort, Quick Sort (First / Random / Median-of-Three)
- 측정 항목: 숫자 비교 횟수, 실행시간(ms), 최대 추가 메모리 사용량(Byte)
- 추가 분석: 데이터 크기 증가에 따른 비교 횟수 및 실행시간 변화, 피벗 선택 방법에 따른 성능 차이, 시간 복잡도와 공간 복잡도 비교

## 구현 내용

### 1. 데이터 생성

- 데이터 크기 `n`마다 원본 배열(`orig`)을 `rand()`를 사용하여 한 번만 생성
- `srand(12345)`를 사용하여 실행할 때마다 동일한 난수 데이터가 생성되도록 설정
- 각 정렬 알고리즘마다 원본 배열을 작업용 배열(`work`)에 복사하여 사용하므로, 모든 알고리즘이 **동일한 데이터**를 정렬
- 데이터 생성과 배열 복사는 비교 횟수 및 실행시간 측정에서 제외
- 데이터 값은 `rand() % 100000`으로 생성하며, 중복된 정수 값 허용

### 2. 정렬 알고리즘

| 알고리즘 | 구현 방식 |
|---|---|
| Heap Sort | 최대 힙(Max Heap)을 구성하고 루트의 최댓값을 배열 끝으로 이동 |
| Merge Sort | 배열을 절반씩 나누어 정렬한 후 임시 배열을 이용하여 병합 |
| Quick Sort (First) | 현재 정렬 구간의 첫 번째 원소를 피벗으로 선택 |
| Quick Sort (Random) | 현재 정렬 구간에서 무작위 위치의 원소를 피벗으로 선택 |
| Quick Sort (Median3) | 첫 번째, 가운데, 마지막 원소 중 중앙값을 피벗으로 선택 |

- **Heap Sort:** 입력 배열 자체를 이용하여 최대 힙을 구성한다. 루트에 위치한 최댓값을 마지막 원소와 교환하고 힙의 크기를 줄인 뒤, `sift_down()`을 호출하여 힙 속성을 복구한다. 모든 원소가 정렬될 때까지 반복한다.
- **Merge Sort:** 배열을 재귀적으로 절반씩 분할하고, 정렬된 두 부분 배열을 임시 배열에 병합한 뒤 원래 배열에 복사한다.
- **Quick Sort (First):** 현재 정렬 구간의 첫 번째 원소를 피벗으로 사용한다.
- **Quick Sort (Random):** `lo + rand() % (hi - lo + 1)`을 통해 현재 정렬 구간에서 무작위 위치를 선택한다.
- **Quick Sort (Median3):** 첫 번째, 가운데, 마지막 원소의 값을 비교하여 중앙값을 피벗으로 선택한다.
- 퀵 정렬은 피벗을 선택하는 부분만 다르게 구현하고, 나머지 분할 알고리즘은 동일하게 유지한다.
- 퀵 정렬은 피벗을 구간의 마지막 위치로 이동시킨 후, 피벗보다 작은 값은 왼쪽, 크거나 같은 값은 오른쪽으로 분할한다.
- 분할이 끝나면 피벗을 최종 위치에 배치하고, 왼쪽과 오른쪽 구간에 대해 재귀적으로 정렬을 수행한다.
- 라이브러리 정렬 함수(`qsort` 등)는 사용하지 않는다.

### 3. 비교 횟수 측정

- **Heap Sort:** 최대 힙 구성 및 `sift_down()` 과정에서 자식 노드와 부모 노드의 값을 비교할 때마다 비교 횟수를 1 증가시킨다.
- **Merge Sort:** 병합 과정에서 두 부분 배열의 원소를 비교할 때마다 비교 횟수를 1 증가시킨다.
- **Quick Sort:** 분할 과정에서 `arr[j] < pivot`을 수행할 때마다 비교 횟수를 1 증가시킨다.
- **Median-of-Three:** 중앙값을 결정하기 위해 발생하는 데이터 값 사이의 비교도 포함한다.
- 비교 결과가 참인지 거짓인지와 관계없이 데이터 값 비교 1회를 계산한다.
- 반복문의 인덱스 및 종료 조건 검사 등 데이터 값 비교가 아닌 연산은 포함하지 않는다.
- 피벗의 무작위 위치 생성과 데이터 이동 및 교환은 비교 횟수에 포함하지 않는다.
- 정렬 결과 검증은 비교 횟수에 포함하지 않는다.
- 각 알고리즘의 비교 횟수를 초기화한 뒤 정렬을 수행하고, 정렬이 끝나면 오름차순 여부를 확인한다.

### 4. 실행시간 측정

- `QueryPerformanceCounter()`를 사용하여 Windows 환경에서 실행시간을 측정한다.
- 정렬 함수 호출 직전부터 정렬이 완료된 시점까지의 시간을 측정한다.
- 데이터 생성, 배열 복사, 결과 출력 및 정렬 검증 시간은 측정에서 제외한다.
- 모든 알고리즘에 동일한 시간 측정 방법과 단위를 적용한다.
- 실행시간은 밀리초(ms) 단위로 출력한다.
- 이번 실험 결과는 각 알고리즘을 한 번씩 실행하여 측정한 값이며, 반복 실행에 따른 평균값은 아니다.

### 5. 메모리 사용량 측정

- 정렬 과정에서 발생하는 최대 추가 메모리 사용량을 Byte 단위로 추정한다.
- **Heap Sort:** `heap_sort()`와 `sift_down()`의 함수 프레임을 기준으로 스택 메모리를 계산한다.
- **Merge Sort:** 병합 과정에서 사용하는 임시 배열의 크기와 재귀 호출에 따른 스택 사용량을 고려한다.
- **Quick Sort:** 피벗 선택 및 재귀 호출 과정에서 사용하는 스택 메모리를 고려한다.
- `ENTER()` 매크로를 이용하여 함수 호출 시 메모리 사용량을 누적하고, `LEAVE()` 매크로를 이용하여 함수 종료 시 감소시킨다.
- 누적 메모리 사용량 중 최댓값을 `mem_max`에 기록한다.
- Merge Sort의 임시 배열은 `n * sizeof(int)`를 기준으로 계산한다.
- 원본 배열과 작업용 배열의 저장 공간은 공통 비용이므로 측정에서 제외한다.
- 측정값은 실제 운영체제의 프로세스 메모리 사용량이 아니라 코드에 정의한 함수 프레임 크기와 동적 할당 메모리를 기준으로 계산한 추정값이다.

## 함수 구성

| 함수 | 역할 |
|---|---|
| `sift_down()` | 최대 힙 속성을 유지하도록 부모 노드와 자식 노드의 위치 조정 |
| `heap_sort()` | 최대 힙을 구성하고 최댓값을 순서대로 배열 끝에 배치 |
| `merge()` | 두 개의 정렬된 부분 배열을 임시 배열을 이용하여 병합 |
| `merge_rec()` | 재귀적으로 배열을 분할하고 병합 정렬 수행 |
| `merge_sort()` | 임시 배열을 생성하고 병합 정렬 시작 |
| `select_pivot()` | 퀵 정렬의 피벗 선택 방법에 따라 피벗 인덱스 결정 |
| `quick_rec()` | 피벗을 기준으로 배열을 분할하고 재귀적으로 정렬 |
| `quick_sort()` | 퀵 정렬 시작 |
| `now_ms()` | 현재 시간을 밀리초 단위로 반환 |
| `run()` | 알고리즘별 비교 횟수, 실행시간 및 메모리 사용량 측정 |
| `main()` | 데이터 생성 → 알고리즘별 정렬 → 결과 출력 |

## 결과 분석

### 1. 데이터 크기 증가에 따른 비교 횟수 변화

- **Heap Sort:** 데이터 크기가 2배가 될 때 비교 횟수는 약 2.17~2.22배 증가하였다. 힙 정렬은 최대 힙을 구성한 뒤 최댓값을 제거하고 힙 속성을 복구하는 과정을 반복한다. 각 단계에서 힙의 높이에 비례하는 비교가 발생하므로 전체적으로 O(n log n)의 증가 추세를 보였다.
- **Merge Sort:** 데이터 크기가 2배가 될 때 비교 횟수는 약 2.17~2.23배 증가하였다. 배열을 절반씩 분할하고 각 단계에서 병합을 수행하기 때문에 데이터 크기가 증가해도 비교 횟수가 비교적 일정한 비율로 증가하였다.
- **Quick Sort (First):** 비교 횟수는 데이터 크기와 피벗 위치에 따라 달라졌다. 이번 실험에서는 20,000개 데이터에서 323,056회가 측정되었다.
- **Quick Sort (Random):** 무작위 피벗을 선택하기 때문에 분할 결과가 달라질 수 있다. 이번 실험에서는 4,000개와 20,000개 데이터에서 다른 퀵 정렬 방식보다 많은 비교 횟수를 기록하기도 했다.
- **Quick Sort (Median3):** 세 원소 중 중앙값을 피벗으로 선택하여 극단적인 피벗이 선택될 가능성을 줄였다. 16,000개 데이터에서는 247,300회로 퀵 정렬 세 방식 중 가장 적은 비교 횟수를 기록하였다.
- 전체적으로 모든 알고리즘에서 데이터 크기가 증가함에 따라 비교 횟수가 증가하였다. 특히 Merge Sort는 모든 데이터 크기에서 가장 적은 비교 횟수를 기록하였다.

### 2. 힙 정렬, 병합 정렬 및 퀵 정렬의 실행시간 차이

- **Heap Sort:** 최대 힙을 구성하고 최댓값을 배열 끝으로 이동시키는 과정을 반복한다. 각 단계에서 힙 속성을 복구하기 위한 비교와 교환이 발생하므로 데이터가 커질수록 실행시간도 증가하였다. 이번 실험에서는 20,000개 데이터에서 3.443ms로 가장 긴 실행시간을 기록하였다.
- **Merge Sort:** 두 부분 배열을 병합할 때 임시 배열에 원소를 복사하고 다시 원래 배열로 이동시키는 작업이 발생한다. 이러한 데이터 이동 작업이 실행시간에 영향을 준 것으로 판단된다.
- **Quick Sort:** 별도의 병합용 임시 배열 없이 배열 내부에서 원소를 교환하면서 정렬한다. 이번 실험에서는 대체로 퀵 정렬이 힙 정렬과 병합 정렬보다 빠른 실행시간을 기록하였다.
- 1,000개 데이터에서는 Quick (Median3)가 0.087ms로 가장 빨랐고, 2,000개 데이터에서는 Heap Sort가 0.173ms로 가장 빨랐다.
- 4,000개 데이터에서는 Quick (Median3)가 0.298ms로 가장 빨랐으며, 8,000개와 16,000개, 20,000개 데이터에서는 Quick (Random)이 각각 0.961ms, 1.654ms, 1.953ms로 가장 빠르게 측정되었다.
- 20,000개 데이터 기준으로 Heap Sort는 3.443ms, Merge Sort는 2.185ms, Quick (First)는 2.153ms, Quick (Random)은 1.953ms, Quick (Median3)는 2.615ms로 측정되었다.
- 따라서 이번 실험에서는 퀵 정렬이 전반적으로 빠른 편이었지만, 피벗 선택 방식에 따라 실행시간 차이가 발생하였다. 특히 Median-of-Three가 항상 가장 빠른 것은 아니며, 실제 분할 결과와 피벗 선택에 필요한 추가 비교도 실행시간에 영향을 준다.

### 3. 힙 정렬, 병합 정렬 및 퀵 정렬의 메모리 사용량 차이

- **Heap Sort:** 입력 배열 자체를 힙으로 사용하며 별도의 임시 배열을 생성하지 않는다. `sift_down()`도 반복문으로 구현했기 때문에 재귀 호출에 따른 스택 증가가 발생하지 않는다. 이번 실험에서는 모든 데이터 크기에서 60 Bytes로 일정하게 측정되었다.
- **Merge Sort:** 병합 과정에서 크기가 n인 임시 배열을 추가로 사용한다. 따라서 데이터 크기가 증가할수록 임시 배열의 메모리 사용량도 증가한다. 여기에 재귀 호출 과정에서 사용하는 스택 메모리가 추가된다.
- **Quick Sort:** 별도의 병합용 배열 없이 원본 배열 내부에서 원소를 교환하며 정렬한다. 따라서 주로 재귀 호출에 따른 스택 메모리가 추가로 사용된다.
- 20,000개 데이터 기준으로 Heap Sort는 60 Bytes, Merge Sort는 80,616 Bytes, Quick (First)는 1,428 Bytes, Quick (Random)은 1,560 Bytes, Quick (Median3)는 1,120 Bytes로 측정되었다.
- Merge Sort는 임시 배열을 사용하기 때문에 다른 알고리즘보다 추가 메모리 사용량이 크게 나타났다.
- Heap Sort는 별도의 배열을 할당하지 않고 반복문으로 힙을 복구하므로 가장 적은 메모리를 사용하였다.
- 퀵 정렬은 재귀 호출 깊이에 따라 메모리 사용량이 달라질 수 있다. 이번 실험에서는 Median-of-Three가 퀵 정렬 세 방식 중 상대적으로 낮은 메모리 사용량을 기록하였다.

### 4. 퀵 정렬의 피벗 선택 방법에 따른 성능 차이

- **First Element:** 현재 정렬 구간의 첫 번째 원소를 피벗으로 선택한다. 구현이 간단하지만 피벗이 최솟값이나 최댓값에 가까운 경우 분할이 한쪽으로 치우칠 수 있다. 이번 실험에서는 20,000개 데이터에서 323,056회의 비교가 발생하였다.
- **Random Pivot:** 현재 정렬 구간에서 무작위 위치의 원소를 피벗으로 선택한다. 특정 위치에 대한 의존성을 줄일 수 있지만 무작위 선택이 항상 균형 잡힌 분할을 보장하지는 않는다. 20,000개 데이터에서는 339,287회로 퀵 정렬 세 방식 중 가장 많은 비교 횟수를 기록하였다.
- **Median-of-Three:** 첫 번째, 가운데, 마지막 원소 중 중앙값을 피벗으로 선택한다. 세 위치의 값을 비교하여 극단적인 피벗이 선택될 가능성을 줄이고 상대적으로 균형 잡힌 분할을 유도한다.
- 16,000개 데이터에서는 Median-of-Three가 247,300회로 퀵 정렬 세 방식 중 가장 적은 비교 횟수를 기록하였다.
- 그러나 20,000개 데이터에서는 Random Pivot이 1.953ms로 가장 빠르게 측정되었으며, Median-of-Three는 2.615ms로 오히려 더 긴 실행시간을 기록하였다.
- 이는 피벗 선택 방식이 비교 횟수뿐 아니라 피벗 선택 과정의 추가 연산과 실제 분할 결과에도 영향을 받기 때문이다.
- 따라서 Median-of-Three가 항상 가장 좋은 성능을 보장하는 것은 아니며, 이번 실험에서는 데이터 크기와 분할 결과에 따라 세 방식의 성능 순서가 달라지는 것을 확인하였다.

### 5. 시간 복잡도 및 공간 복잡도 비교

| 알고리즘 | 평균 시간 복잡도 | 최악 시간 복잡도 | 추가 공간 복잡도 |
|---|---|---|---|
| Heap Sort | O(n log n) | O(n log n) | O(1) |
| Merge Sort | O(n log n) | O(n log n) | O(n) |
| Quick Sort (First) | O(n log n) | O(n²) | 평균 O(log n), 최악 O(n) |
| Quick Sort (Random) | O(n log n) | O(n²) | 평균 O(log n), 최악 O(n) |
| Quick Sort (Median3) | O(n log n) | O(n²) | 평균 O(log n), 최악 O(n) |

- **Heap Sort:** 최대 힙을 구성하는 데 O(n)의 시간이 필요하고, 이후 n개의 원소를 하나씩 제거하면서 힙 속성을 복구한다. 각 복구 과정은 O(log n)이므로 전체 시간 복잡도는 O(n log n)이다. 입력 배열 내부에서 힙을 구성하므로 추가 공간은 O(1)이다.
- **Merge Sort:** 배열을 절반씩 분할하고 각 단계에서 병합하는 과정을 반복한다. 분할 단계는 log n이고 각 단계에서 전체 n개의 원소를 처리하므로 시간 복잡도는 최선, 평균, 최악의 경우 모두 O(n log n)이다. 다만 병합을 위한 임시 배열이 필요하므로 추가 공간 복잡도는 O(n)이다.
- **Quick Sort:** 피벗을 기준으로 배열을 분할하고 양쪽 구간을 정렬한다. 분할이 균형 있게 이루어지면 평균적으로 O(n log n)의 시간 복잡도를 갖지만, 한쪽으로 치우친 분할이 반복되면 O(n²)의 최악 시간 복잡도가 발생한다.
- 퀵 정렬은 평균적으로 재귀 호출 스택에 O(log n)의 공간을 사용하지만, 최악의 경우 재귀 깊이가 n에 가까워져 O(n)의 공간이 필요할 수 있다.
- 피벗 선택 방법은 평균적인 분할의 균형에 영향을 줄 수 있지만, First, Random, Median-of-Three 모두 이론적인 최악 시간 복잡도는 O(n²)이다.

### 6. 메모리 사용량 측정 방법과 계산 기준

이번 실험에서는 정렬 과정에서 발생하는 최대 추가 메모리 사용량을 추정하기 위해 함수 호출에 따른 스택 프레임과 동적 할당 메모리를 고려하였다.

- **Heap Sort:** `heap_sort()`와 `sift_down()` 함수의 프레임 크기를 기준으로 메모리 사용량을 계산하였다. 힙 정렬은 반복문으로 힙 속성을 복구하기 때문에 재귀 호출에 따른 스택 증가가 없다.
- **Merge Sort:** 병합 과정에서 사용하는 임시 배열의 크기를 `n * sizeof(int)`로 계산하고, `merge_sort()`, `merge_rec()`, `merge()`의 함수 호출 과정에서 추정한 스택 사용량을 더하였다.
- **Quick Sort:** `quick_sort()`, `quick_rec()`, `select_pivot()`의 함수 호출 과정에서 추정한 스택 사용량을 기준으로 계산하였다.
- 함수 호출 시 `ENTER()` 매크로로 메모리 사용량을 누적하고, 함수 종료 시 `LEAVE()` 매크로로 감소시켰다. 누적 메모리 사용량 중 최댓값을 `mem_max`에 기록하였다.
- 함수 프레임 크기는 코드에 정의한 포인터, 정수형 지역 변수 및 반환 주소 등의 크기를 기준으로 추정하였다.

20,000개 데이터에서 Merge Sort의 메모리 사용량은 80,616 Bytes이다. 이 중 임시 배열은 `20,000 * sizeof(int)`로 계산되며, 일반적인 4 Byte 정수 환경에서는 80,000 Bytes이다. 나머지 616 Bytes는 코드에서 정의한 함수 프레임 크기를 기준으로 추정한 스택 사용량이다.

Heap Sort는 별도의 임시 배열을 할당하지 않으며, 반복문을 사용하여 힙 속성을 복구하기 때문에 모든 데이터 크기에서 60 Bytes로 동일하게 측정되었다.

Quick Sort는 별도의 임시 배열을 사용하지 않으므로 재귀 호출에 따른 스택 사용량이 주된 추가 메모리 사용량이다.

단, 본 실험의 메모리 사용량은 실제 운영체제의 스택 사용량이나 프로세스 전체 메모리를 직접 측정한 값이 아니다. 코드에 정의한 함수 프레임 크기와 동적 할당 크기를 기준으로 계산한 추정값이며, 실제 메모리 사용량은 컴파일러의 최적화 설정과 함수의 스택 프레임 구성 등에 따라 달라질 수 있다.

## 결론

이번 과제에서는 무작위 정수 데이터 n = 1,000 ~ 20,000에 대해 힙 정렬, 병합 정렬 및 세 가지 피벗 선택 방법을 사용하는 퀵 정렬의 비교 횟수, 실행시간, 메모리 사용량을 측정하고 성능을 분석하였다.

- **비교 횟수:** Merge Sort는 모든 데이터 크기에서 가장 적은 비교 횟수를 기록하였다. 배열을 일정하게 절반씩 분할하고 병합하는 방식이 비교 횟수의 안정적인 증가에 영향을 준 것으로 판단된다.
- **실행시간:** Quick Sort는 대부분의 데이터 크기에서 빠른 실행시간을 기록하였다. 특히 20,000개 데이터에서는 Quick (Random)이 1.953ms로 가장 빨랐다. 반면 Heap Sort는 3.443ms로 가장 긴 실행시간을 기록하였다.
- **메모리 사용량:** Heap Sort는 입력 배열 자체를 힙으로 사용하고 반복문으로 힙 속성을 복구하므로 60 Bytes로 일정한 메모리 사용량을 기록하였다. Merge Sort는 임시 배열을 사용하기 때문에 데이터 크기가 증가할수록 메모리 사용량도 증가하였다.
- **피벗 선택 방법:** First Element는 피벗 위치에 따라 분할이 한쪽으로 치우칠 수 있고, Random Pivot은 무작위 선택으로 인해 분할 결과가 달라질 수 있다. Median-of-Three는 세 원소의 중앙값을 선택하여 상대적으로 균형 잡힌 분할을 유도하지만, 항상 가장 빠른 결과를 보장하지는 않았다.
- **시간 및 공간 복잡도:** Heap Sort는 O(n log n)의 시간 복잡도와 O(1)의 추가 공간 복잡도를 가진다. Merge Sort는 최악의 경우에도 O(n log n)의 시간 복잡도를 유지하지만 O(n)의 추가 공간이 필요하다. Quick Sort는 평균 O(n log n)의 시간 복잡도와 평균 O(log n)의 추가 스택 공간을 갖지만, 최악의 경우 시간 복잡도는 O(n²), 공간 복잡도는 O(n)까지 증가할 수 있다.
- **메모리 측정:** 임시 배열과 함수 호출에 따른 스택 프레임을 기준으로 추가 메모리 사용량을 추정하였다. 실제 프로세스 전체 메모리 사용량과는 차이가 있을 수 있지만, 알고리즘별 메모리 구조 차이를 비교하는 데 활용하였다.

종합적으로 이번 실험에서는 Merge Sort가 비교 횟수 측면에서 가장 적은 연산을 수행하였으며, Heap Sort는 가장 적은 추가 메모리를 사용하였다. Quick Sort는 실행시간 측면에서 전반적으로 유리한 결과를 보였지만, 피벗 선택 방법에 따라 성능 차이가 발생하였다.

이를 통해 정렬 알고리즘의 성능은 단순히 비교 횟수만으로 결정되는 것이 아니라, 데이터 이동, 임시 메모리 사용, 힙 속성 복구, 피벗 선택에 따른 분할 균형 및 재귀 호출 깊이 등 여러 요소의 영향을 받는다는 것을 확인하였다.
