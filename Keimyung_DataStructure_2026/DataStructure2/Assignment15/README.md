# [자료구조2] Assignment 15 - 퀵 정렬과 AVL 트리 정렬의 성능 비교
## 과제

동일한 무작위 정수 데이터에 대해 퀵 정렬(Quick Sort)과 AVL 트리 정렬(AVL Tree Sort)을 수행한 뒤, 정렬된 상태에서 삽입·삭제를 반복하고, **정렬부터 삽입·삭제까지의 전체 과정**에서 발생하는 실행시간, 비교 횟수, 데이터 이동 횟수, 메모리 사용량을 비교·분석한다.

- 데이터 크기: n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 데이터 구성: 무작위 정수 (중복 허용)
- 삽입·삭제 횟수: 최초 데이터 크기 n의 20% (200 / 400 / 800 / 1,600 / 3,200 / 4,000회)
- 정렬 기준: 오름차순
- 구현 자료구조: 정렬된 배열(퀵 정렬 + 선형 탐색 삽입·삭제), AVL 트리(중복은 `count`로 저장)
- 측정 항목: 총 수행시간(ms), 비교 횟수, 데이터 이동 횟수, 최대 메모리 사용량(Byte), 최종 데이터 개수
- 추가 분석: 수행시간·비교 횟수 차이, 데이터 이동 횟수 차이, 메모리 사용량 차이, 데이터 크기 증가에 따른 성능 변화, 삽입·삭제가 반복되는 환경에서 유리한 자료구조

## 구현 내용

### 1. 데이터 생성

- 데이터 크기 `n`마다 원본 배열(`data`)을 한 번만 생성하고, 퀵 정렬(배열)과 AVL 트리가 **동일한 원본 데이터**를 사용
- 난수는 직접 구현한 `xorshift64*` 생성기(`nextRandom()`)를 사용하며 시드는 `20240615 + n`으로 고정하여, 실행할 때마다(컴파일러·OS가 달라도) 동일한 데이터가 생성됨
- 데이터 값은 `1 ~ n` 범위의 정수이며 중복된 값을 허용 (n개를 뽑으면 서로 다른 값은 약 63%)
- 삽입·삭제 연산 목록(`ops`)도 데이터와 함께 미리 한 번만 생성하여 두 자료구조에 **같은 순서, 같은 값**으로 적용
- 난수 생성 및 결과 출력 시간은 측정에서 제외

### 2. 정렬 및 데이터 조작

| 자료구조 | 구현 방식 |
|---|---|
| 퀵 정렬 + 배열 | 원본 데이터를 배열에 복사한 뒤 퀵 정렬로 오름차순 정렬, 이후 삽입·삭제는 정렬된 배열에서 직접 수행 |
| AVL 트리 | 원본 데이터를 하나씩 AVL 트리에 삽입하여 정렬 상태를 유지, 이후 삽입·삭제도 트리에서 직접 수행 |

- **퀵 정렬 (피벗 선택 방법: Median-of-Three):** 구간의 첫 번째, 가운데, 마지막 원소를 서로 비교·교환하여 중앙값을 피벗으로 사용한다. 분할은 Hoare 방식(`i`, `j` 두 인덱스가 양 끝에서 접근)이며, 재귀 대신 명시적 스택(`Range stk[64]`)을 사용하고 **작은 구간을 먼저 처리**하여 스택 깊이를 O(log n)으로 제한한다.
- **배열 삽입:** 삽입할 값보다 작은 원소가 끝나는 위치까지 선형 탐색한 뒤, 그 위치부터 뒤의 원소를 한 칸씩 뒤로 이동하고 값을 저장한다. 용량이 가득 차면 2배 크기의 새 배열로 확장한다.
- **배열 삭제:** 삭제할 값을 선형 탐색하여 찾은 뒤 뒤의 원소를 한 칸씩 앞으로 이동한다. 값이 없으면 삭제하지 않고 다음 연산으로 진행한다.
- **AVL 트리:** 노드에 `key`, `count`(중복 횟수), `height`, `left`, `right`를 저장한다. 이미 있는 값을 삽입하면 새 노드를 만들지 않고 `count`만 1 증가시키고, 삭제할 때도 `count`가 2 이상이면 1만 감소시켜 **한 개의 원소만** 제거한다. 삽입·삭제 후 되돌아오면서 균형 인수를 확인하고 LL, RR, LR, RL 회전으로 균형을 복구한다. 자식이 둘인 노드를 삭제할 때는 오른쪽 서브트리의 최솟값 노드(후속자)를 분리하여 그 값을 현재 노드에 복사한다.
- 라이브러리 정렬 함수(`qsort` 등)는 사용하지 않는다.
- 모든 연산이 끝난 뒤 AVL 트리를 중위 순회(`inorderFill()`)하여 배열로 펼치고, 퀵 정렬 배열과 **원소 개수, 모든 원소 값이 동일한지, 오름차순인지** 검증한다. 검증은 측정에서 제외한다.

### 3. 삽입·삭제 실험

- 연산 횟수는 `n / 5`회이다.
- 각 연산마다 난수를 하나 뽑아 **짝수이면 삽입, 홀수이면 삭제**를 선택하고, 실제로 삽입·삭제할 값은 별도의 난수로 생성한다.
- 삭제할 값이 존재하지 않으면 삭제하지 않고 다음 연산으로 진행한다. (`n`이 1~n 범위이고 중복이 있으므로 삭제 대상이 존재하는 경우가 많다.)
- 최종 데이터 개수는 두 자료구조가 항상 같아야 하며, 실제로 모든 크기에서 같게 측정되었다.

### 4. 비교 횟수 측정

- **퀵 정렬/배열:** Median-of-Three의 세 원소 비교, 분할 과정의 `data[i] < pivot`, `pivot < data[j]` 비교, 삽입·삭제 시 선형 탐색의 `data[pos] < value` 비교를 `arrayLess()`에서 한 번 수행할 때마다 1 증가시킨다. 삭제할 때 찾은 위치의 값이 같은지 확인하는 `!=` 비교도 1회로 센다.
- **AVL 트리:** 노드를 방문할 때 실제로 수행한 값 비교를 각각 1회로 센다. `value < node->key`가 참이면 1회, 거짓이면 이어서 `value > node->key`를 수행하므로 2회이다(같은 값이면 2회).
- 균형 인수·높이 비교, 반복문 인덱스 검사, 포인터 `NULL` 검사 등 데이터 값과 무관한 비교는 포함하지 않는다.
- 후속자를 찾는 `detachMin()`은 포인터를 따라 내려가기만 하므로 값 비교가 없다.

### 5. 데이터 이동 횟수 측정

| 동작 | 이동 횟수 |
|---|---|
| 퀵 정렬 `swap` | 3회 (임시 변수 저장 + 두 번 대입) |
| 퀵 정렬 피벗 값 복사 | 1회 |
| 배열 삽입·삭제 시 원소 한 칸 이동 | 원소당 1회 |
| 배열 삽입 시 새 값 저장 | 1회 |
| 배열 용량 확장 시 기존 원소 복사 | 원소당 1회 |
| AVL 새 노드 생성 시 키 저장 | 1회 |
| AVL 삭제 시 후속자 키를 현재 노드에 복사 | 1회 |

- AVL의 포인터 연결 변경(회전 포함), `count`, `height` 갱신은 데이터 값의 이동이 아니므로 제외한다.

### 6. 실행시간 측정

- `timespec_get()`으로 정렬 시작 직전(AVL은 첫 삽입 직전)부터 **마지막 삽입·삭제가 끝난 시점**까지의 시간을 ms 단위로 측정한다.
- 배열에 원본 데이터를 복사하는 시간, 난수 생성, 검증, 결과 출력 시간은 제외한다.
- 시간은 같은 입력으로 **5회 반복 실행한 평균값**이다. 비교·이동 횟수와 메모리는 반복해도 항상 같은 값이다.

### 7. 메모리 사용량 측정

- 자료구조와 보조 공간을 포함한 **최대 메모리 사용량**을 Byte 단위로 계산한다. (실제 프로세스 메모리 측정값이 아니라 코드 기준 계산값이다.)
- **배열 + 퀵 정렬:** `배열 용량 × sizeof(int)`에 퀵 정렬 스택(`Range` 8 Byte × 사용 깊이)을 더한다. 삽입 중 용량이 가득 차 2배로 확장할 때는 기존 배열과 새 배열이 동시에 존재하므로 `(기존 용량 + 새 용량) × 4 Byte`를 최댓값 후보로 기록한다.
- **AVL 트리:** `최대 노드 수 × sizeof(Node)(32 Byte) + 재귀 최대 깊이 × sizeof(Node*)(8 Byte)`로 계산한다. 재귀 스택은 추정치이다.
- AVL 트리를 배열로 펼치는 검증용 버퍼와 원본 데이터(`data`)는 공통 비용 또는 검증용이므로 제외한다.

## 함수 구성

| 함수 | 역할 |
|---|---|
| `nextRandom()` | 시드 고정 `xorshift64*` 난수 생성 |
| `arrayInit()` / `arrayFree()` | 배열에 원본 데이터 복사 / 메모리 해제 |
| `arrayLess()` | 데이터 값 비교 1회를 수행하고 비교 횟수 증가 |
| `arraySwap()` | 두 원소 교환, 이동 횟수 3 증가 |
| `arrayPartition()` | Median-of-Three로 피벗을 정하고 Hoare 방식으로 분할 |
| `arrayQuickSort()` | 명시적 스택을 이용한 퀵 정렬 (작은 구간 우선 처리) |
| `arrayGrow()` | 배열 용량 2배 확장 |
| `arrayInsert()` / `arrayErase()` | 정렬된 배열에서 선형 탐색 후 삽입·삭제 |
| `insertNode()` / `removeNode()` | AVL 트리 삽입 / 삭제 (중복은 `count`로 처리) |
| `detachMin()` | 서브트리의 최솟값 노드(후속자)를 분리 |
| `rotateLeft()` / `rotateRight()` / `rebalance()` | 회전으로 AVL 균형 복구 |
| `avlInsert()` / `avlErase()` | AVL 삽입·삭제 호출 및 메모리 최댓값 갱신 |
| `inorderFill()` | 중위 순회로 AVL 트리를 오름차순 배열로 변환 (검증용) |
| `runQuick()` / `runAvl()` | 자료구조별 정렬, 삽입·삭제, 측정값 반환 |
| `isSortedAscending()` | 오름차순 검증 |
| `printResult()` | 두 자료구조의 측정 결과를 형식에 맞춰 출력 |
| `main()` | 데이터·연산 생성 → 퀵 정렬 / AVL 실행 → 검증 → 5회 반복 시간 측정 → 출력 |

## 결과 분석

### 1. 총 수행시간 및 비교 횟수 차이

- 정렬 단계만 보면 두 방법의 비교 횟수는 거의 같다. n=20,000에서 퀵 정렬은 383,477회, AVL 트리 구축은 374,751회로, 둘 다 O(n log n) 수준이다.
- 차이는 **삽입·삭제 단계**에서 생긴다. 정렬된 배열은 삽입 위치와 삭제 대상을 선형 탐색(O(n))으로 찾으므로 연산 1회당 평균 약 n/2번 비교한다. n=20,000에서 4,000회 연산에 약 4,068만 회(연산당 약 10,170회)가 발생했다. AVL 트리는 루트에서 트리 높이(O(log n))만큼만 내려가므로 같은 4,000회 연산에 약 8.1만 회(연산당 약 20회)로 충분했다.
- 그 결과 전체 비교 횟수는 n=1,000에서 7.5배, n=20,000에서 90.1배 차이가 나며, n이 커질수록 격차가 벌어졌다.
- 총 수행시간도 같은 방향이다. n=1,000에서는 AVL이 1.7배(1.039ms vs 0.625ms) 빨랐지만 n=20,000에서는 27.2배(463.699ms vs 17.027ms) 빨랐다. 배열 쪽은 삽입·삭제 때마다 수천 개 원소를 비교하고 이동하는 반복이 시간의 대부분을 차지한다.
- 시간의 배율(27배)이 비교 횟수의 배율(90배)보다 작은 이유는 시간에 노드 생성(`malloc`)과 포인터 탐색 비용이 포함되기 때문이다. 배열은 연속된 메모리를 순차적으로 접근하므로 비교 한 번의 비용이 작고, AVL은 노드를 따라 이동하며 메모리 할당과 회전·높이 갱신 비용이 추가된다. 또한 Debug 빌드에서는 비교마다 호출되는 `arrayLess()` 등이 인라인되지 않아 비교 횟수가 많은 배열 쪽 부담이 더 크게 나타난 것으로 보인다.

### 2. 삽입·삭제 과정에서 발생하는 데이터 이동 횟수 차이

- 배열은 삽입·삭제마다 해당 위치 뒤의 원소를 모두 한 칸씩 이동해야 한다. 위치가 균등하게 분포하므로 평균적으로 원소의 절반이 이동한다. n=20,000에서 삽입·삭제 4,000회 동안 약 3,361만 회(연산당 약 8,400회)의 이동이 발생했다.
- AVL 트리는 값을 옮기지 않고 포인터만 연결한다. 값 이동은 새 노드를 만들 때 키를 저장하는 경우와, 자식이 둘인 노드를 삭제하며 후속자의 키를 복사하는 경우뿐이다. 같은 4,000회 동안 이동은 1,000회에 불과했다. 균형을 맞추는 회전은 포인터 변경이므로 이동 횟수에 포함되지 않는다.
- 중복 값이 이미 있는 노드에 삽입하는 경우(`count` 증가)와 `count`가 2 이상인 노드의 삭제는 값 이동이 0회이므로, 중복이 많은 데이터일수록 AVL의 이동 횟수는 더 줄어든다.
- 전체 이동 횟수는 n=1,000에서 138배, n=20,000에서 2,489배 차이가 났다. 정렬 단계의 이동 횟수(퀵 242,108회 vs AVL 12,598회)도 퀵 정렬의 `swap`(3회씩)이 더 많아 AVL이 적었다.

### 3. 배열과 AVL 트리의 메모리 사용량 차이

- 메모리는 이번 실험에서 **AVL 트리가 더 많이 사용**한다. 모든 크기에서 AVL은 배열의 약 1.7배(1.68~1.73배)를 사용했다.
- AVL은 값 하나(4 Byte)를 저장하기 위해 `key`, `count`, `height`(각 4 Byte)와 `left`, `right` 포인터(각 8 Byte)를 가진 32 Byte 노드를 사용한다. 중복 값을 `count`로 합쳐도 노드 수는 서로 다른 값의 개수(약 0.63n)여서 약 20n Byte가 된다.
- 배열은 원소당 4 Byte만 사용하므로 구조적으로 메모리 효율이 좋다. 다만 최대값이 12n Byte로 측정된 것은 첫 삽입에서 용량(n)이 가득 차 2배로 확장하는 순간 기존 배열(n)과 새 배열(2n)이 동시에 존재하기 때문이다. 확장 이후 실제로 유지되는 크기는 8n Byte이다. 퀵 정렬 스택은 작은 구간을 먼저 처리하므로 최대 십여 개 항목(100 Byte 안팎)에 그쳐 전체에 거의 영향을 주지 않는다.
- AVL의 재귀 스택은 트리 높이(n=20,000에서 20 안팎)만큼만 쌓이므로 노드 메모리(약 400KB)에 비해 무시할 수 있는 수준이다.
- 정리하면, 배열은 메모리 효율이 좋고 AVL은 포인터와 균형 정보로 인한 원소당 오버헤드가 크다. 비율이 n과 무관하게 거의 일정한 것도 노드 구조의 크기가 고정이기 때문이다.

### 4. 데이터 크기 증가에 따른 성능 변화

- **배열(퀵 정렬):** n이 2배가 되면 비교 횟수와 이동 횟수가 약 4배(비교 3.85~4.00배, 이동 3.73~4.10배)로 늘었다. 삽입·삭제 횟수가 n에 비례해 늘고, 연산 1회의 비용도 n에 비례하므로 삽입·삭제 단계 전체가 **O(n²)** 로 증가하기 때문이다.
- **AVL 트리:** n이 2배가 되면 비교 횟수가 약 2.15~2.27배, 이동 횟수가 약 2배로 늘었다. 연산 횟수가 2배가 될 때 연산당 비용은 log n만큼만 커지므로 **O((n+k) log n)** 에 가까운 증가이다.
- 시간은 AVL이 n이 2배가 될 때마다 약 2배(1.98~2.09배)로 꾸준히 증가했다. 배열은 대체로 급격히 증가했지만 일부 구간(2,000→4,000에서 2.5배, 4,000→8,000에서 5.7배)은 이론값 4배와 차이가 있다. 이는 실행시간이 ms 단위로 작은 값이고 운영체제 스케줄링, 캐시 상태, Debug 빌드 등의 영향을 받기 때문으로 보이며, 비교·이동 횟수는 이런 영향 없이 이론과 잘 맞았다.
- 결과적으로 n이 커질수록 두 자료구조의 격차는 계속 벌어졌다. (시간 기준 1.7배 → 27.2배, 비교 기준 7.5배 → 90.1배)
- 메모리는 둘 다 O(n)으로 선형 증가하며 비율은 일정했다.

### 5. 삽입·삭제가 반복되는 환경에서 유리한 자료구조

| 연산 | 정렬된 배열 | AVL 트리 |
|---|---|---|
| 정렬 / 구축 | 퀵 정렬 평균 O(n log n), 최악 O(n²) | O(n log n) |
| 탐색 | 선형 탐색 O(n) (이진 탐색을 쓰면 O(log n)) | O(log n) |
| 삽입 | 위치 탐색 + 원소 이동 O(n) | O(log n), 회전 최대 2회 |
| 삭제 | 대상 탐색 + 원소 이동 O(n) | O(log n), 회전은 경로 상에서 발생 |
| 추가 공간 | 스택 O(log n), 확장 시 기존+신규 배열 | 노드마다 포인터 2개와 `count`, `height` 필요 |

- **삽입·삭제가 반복되는 환경에서는 AVL 트리가 유리하다.** 정렬된 배열은 이진 탐색으로 위치를 빠르게 찾더라도 뒤의 원소를 모두 밀어야 하므로 연산당 O(n)을 피할 수 없다. 반면 AVL 트리는 경로를 따라 내려가 포인터만 바꾸고, 불균형이 생기면 회전 몇 번으로 높이를 O(log n)으로 유지하므로 **연산당 O(log n)을 항상 보장**한다.
- 실험에서도 n=20,000 기준으로 비교 횟수 90배, 이동 횟수 2,489배, 수행시간 27배 차이가 나타났고, n이 커질수록 격차가 커졌다.
- 반대로 AVL은 노드 구조 때문에 메모리를 약 1.7배 더 쓰고 연산 1회의 상수 비용(노드 할당, 회전, 높이 갱신)이 크다. 삽입·삭제가 거의 없고 정렬 결과를 한 번만 읽는 경우에는 메모리가 적고 순차 접근이 빠른 배열이 더 적합할 수 있다. 하지만 이번 실험처럼 n의 20%에 해당하는 삽입·삭제가 반복되는 상황에서는 메모리 증가를 감수하더라도 AVL 트리가 더 효율적이다.

## 결론

이번 과제에서는 동일한 무작위 정수 데이터 n = 1,000 ~ 20,000에 대해 정렬된 배열(퀵 정렬)과 AVL 트리에서 정렬과 삽입·삭제를 수행하고 수행시간, 비교 횟수, 데이터 이동 횟수, 메모리 사용량을 비교하였다.

- **비교 횟수:** 정렬 단계는 두 방법이 비슷했지만(퀵 383,477회, AVL 374,751회), 삽입·삭제 단계에서 배열은 선형 탐색으로 연산당 약 10,170회, AVL은 약 20회를 비교하여 n=20,000에서 전체 비교 횟수가 90.1배 차이 났다.
- **데이터 이동 횟수:** 배열은 삽입·삭제마다 원소를 밀어야 해서 33,848,230회가 발생했고, AVL은 포인터만 바꾸어 13,598회에 그쳤다. n=20,000에서 2,489배 차이다.
- **실행시간:** AVL이 모든 크기에서 빨랐고 n=20,000에서 17.027ms 대 463.699ms로 27.2배 차이 났다. n이 2배가 될 때 AVL은 약 2배, 배열은 이론상 약 4배로 증가하여 격차가 벌어졌다.
- **메모리 사용량:** 배열은 원소당 4 Byte로 효율적이지만 확장 시 일시적으로 12n Byte가 필요했고, AVL은 32 Byte 노드를 사용해 약 1.7배(405,160 Byte 대 240,000 Byte)를 사용했다. 메모리는 AVL이 불리했다.
- **데이터 크기 증가:** 배열의 삽입·삭제 비용은 O(n²), AVL은 O((n+k) log n)에 가까운 증가를 보였고, n이 커질수록 AVL의 이점이 커졌다.
- **정확성:** 모든 크기에서 배열과 AVL 트리의 최종 데이터가 개수와 값까지 동일하고 오름차순임을 확인하였다.
- **측정의 한계:** 실행시간은 Visual Studio x64 Debug 환경에서 5회 평균으로 측정한 값이라 환경과 빌드 설정에 따라 달라질 수 있다. 메모리는 실제 프로세스 사용량이 아니라 자료구조 크기와 스택 추정값으로 계산한 값이며, 비교·이동 횟수는 위에 정의한 기준(AVL의 `count`, `height`, 포인터 변경 제외 등)에 따른 값이다.

종합적으로 삽입·삭제가 반복되는 환경에서는 메모리를 더 쓰더라도 **연산당 O(log n)을 보장하는 AVL 트리**가 연속 배열보다 훨씬 효율적이며, 배열은 구조가 단순하고 메모리 효율이 좋지만 데이터 이동 비용 때문에 변경이 잦은 환경에는 적합하지 않다는 것을 과제15로 확인하였다.
